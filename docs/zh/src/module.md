# 模块

> 本章描述 Co 的模块设计方向。自 **0.2.0** 起，`public` 关键字已部分实装（词法/语法/语义 + 动态库导出、尚不改 linkage、**不参与跨模块可见性**）；`import` 与模块间依赖仍未实装。本章末尾「当前实装边界」给出此刻可依赖的真实模型。

## 一个文件即一个模块

按设计，**一个 `.co` 源文件就是一个模块**。模块是 Co 组织程序、划定接口边界的基本单位：一个模块内定义的名称，默认属于该模块；要让别的模块使用，需显式标 `public`。

模块**默认以其文件的名称命名**（即去掉扩展名的文件名）；导入时可用 `as` 为它另起本地别名（见「import（模块导入）」章节）。

设置模块的目的在于支持大工程组织、并避免陷入 C/C++ 头文件（`.h`/`.cpp`）分离带来的重复定义与同步成本。

## 对外接口：`public`

- `public` 是 Co **唯一的可见性关键字**——没有 `private`，也不另设 `export`。它同时承担两件事：标记**模块接口**（可被其他模块导入）与**动态库导出**。
- 未标 `public` 的定义仅在模块内部可见；标了 `public` 才对外可见、才可被导入。
- `public` 可修饰函数、`class`、`struct` 及类成员（详见「函数定义」「class」章节）。

## 模块的形态（设计方向）

一个模块在物理上可以表现为不同的产物形态：

| 形态 | 说明 | 状态 |
| --- | --- | --- |
| `.co` | 源文件模块，最直接的形式 | 设计核心（编译器尚未支持 `import` 消费它） |
| `.bc` | LLVM bitcode 目标文件 | 设计方向·未实现 |
| `.dll` / `.so` | 原生动态库 | 远期设想·未实现 |

> **为何 `.bc`/`.dll` 作模块并非「拿来就能用」**：`import` 需要的是**编译期的声明信息**（函数原型、类型定义、哪些名字对外可见），而 `.bc`/`.dll` 本质是**链接期的符号定义**。要让一个二进制产物成为「可被导入的模块」，它必须**额外携带自身的接口/声明元数据**——这套载体目前基准未定义、编译器也未实装。现阶段链接多个 `.bc` 只是把它们合并链接，并不能从中恢复可导入的声明。

## 尚未定稿

以下关键点在基准中都**尚未定稿**，故本章只给方向、不给语法细节：

- 跨模块名称可见性的完整规则（裸名能否跨模块、`public` 的导出粒度）；
- `.bc`/`.dll` 形态如何携带并校验接口声明；
- 模块名与路径的解析方式、依赖环的处理；
- 模块顶层代码在跨模块加载时的执行时机与次数（单模块的入口与顶层执行模型见「程序入口与执行」章节）；
- 模块落地后文件级 `static` 的去留，以及它与「省略 `public` = 模块内部」如何并存（`static` 在基准里仅作类的静态成员修饰符）。

这些要等模块系统在当前代编译器实装时连同语义一并定稿后再补写。导入机制的语法另见「import（模块导入）」章节。

## 当前实装边界

自 **0.2.0** 起：

- `public` 可修饰顶层函数与全局变量；产物为动态库时写入导出表（`DLLExportStorageClass`）；`static public` 混序合法。本阶段 `public` **不改变 linkage**，也**不开放**作为跨模块可见性标记（需 `import` 同批落地）。现阶段同一产物内多文件的可见性仍沿用 C 链接规则：`static` 限本翻译单元、其余对外可见。**注意**：在 Co 目标模型里，「模块内部」是以**省略 `public`** 表达的，而非 `static`；`static` 在基准中仅作类的静态成员修饰符。
- 动态库产物：无 `-shared` 选项，但链接层将用户输出路径原样交由 `clang`，驱动按 `-o` 扩展名自动切 DLL/exe；将输出取为 `*.dll` 即可产出含导出表的动态库（Windows 实测）。
- 每个 `.co` 仍被当作一个独立**翻译单元**编译，`#include` 提供的文本声明在该单元内可见；跨文件复用仍走编译期 + 链接期方式（具体见「编译器命令行」章节的「多文件程序」）。
- `import` 仍未实装（现状见「import（模块导入）」章节）；模块顶层代码在跨模块加载时的执行时机与次数仍待与 `import` 同批定稿（单模块入口模型见「程序入口与执行」章节）。
